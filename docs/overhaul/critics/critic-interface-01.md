# Independent interface critique 01

Reviewed 2026-09-06. Blind review of the supplied rendered captures and a limited UI/input/CSS inspection. No narratives or other critics were read, no browser was opened, and no source was edited. Scores describe the observed interface, not the existence of code or the quality of concept paintings. A PASS requires clear primary actions and information at the supplied device sizes, with no unresolved critical interaction issue.

## Verdict and scores

**Overall: FAIL — 4.6/10.** Desktop menu composition is substantially clearer than combat operation. The current interface has a consistent navy/cream/gold palette and useful selected states, but too much gameplay information is effectively microprint. The reference concepts communicate actions through large pictograms, readable resource groups, and strong spatial relationships; the actual captures predominantly communicate them through small text in thin rectangular panels.

## Five highest-value correctives

1. **P1 — Make the interruption/focus path visibly reliable.** `interface-pause-desktop.png` contains a full-screen scrim with no visible log, controls, pause title, or way back to the helm. The source intends a 0.2-second sliding drawer (`src/styles.css:1239–1256`), so the capture may be an initial animation frame; it is not proof of a permanently missing drawer. Supply a settled pause capture before accepting this state, and ensure a visible pause/resume action exists immediately when input becomes blocked. Separately, fix the definite keyboard behavior: the intro's global Enter handler launches regardless of the focused ship button (`src/ui/Hud.ts:1017–1028`), so Tab to an unselected ship then Enter can launch the previous selection. Contract/build changes replace the entire panel DOM (`src/ui/VoyagePanel.ts:159,169–178`), dropping focus; preserve the selected control's focus, focus the first meaningful control when a dialog opens, and restore the invoking control on close. The existing focus trap and pause/input clearing are useful foundations, but do not repair those focus transitions. Acceptance: keyboard-only ship selection, contract/build selection, pause, resume, and return-to-menu can be completed with visible focus and no unexpected launch.

2. **P1 — Recompose mobile information instead of shrinking it.** `interface-contracts-mobile.png` fits the complete form, but risk/reward metadata is 5px in the CSS, descriptions 8–9px, and section hints 6px (`src/styles.css:2170–2190`). The user must read those values to make the decision. Dock ship subtitles and gameplay crew counts are similarly minute. Use at least roughly 12–14px for decision-making labels and descriptions, let the form scroll, shorten secondary prose, and keep a sticky primary action. In the 844×390 landscape capture, the center hull panel and compass stack directly over the player's mast/sail, and the large bottom-center lookout callout competes with the playing field. Move those into deliberate edge zones, reduce persistent noncritical callouts, and reserve the center for target/ship silhouettes. The supplied final landscape state has no evident button-to-button overlap; the remaining problem is scene occlusion, tiny text, and density. Landscape also hides sails, crew condition, sailing speed/throttle, and special recharge status in CSS (`src/styles.css:2422–2426,2444–2453`); restore a compact way to read those conditions before asking the player to use repair, sail, or special controls. Acceptance: actual-size portrait and landscape screenshots remain legible without zoom, including while aiming or receiving a callout.

3. **P1 — Make aiming show the correction and the expected impact.** In `interface-aim-desktop-final.png`, the enemy is visible, but the centered crosshair and long fine gold diagonals appear disconnected from it. `TARGET OUTSIDE FIRING ARC` identifies the failure but does not communicate which way/how far to turn. Put a high-contrast bracket on the target, show a clear lateral bearing/turn cue and a labeled impact footprint on the sea, and strengthen the firing-sector edges enough to survive bright foam. Distinguish `battery loaded` from `target in arc` and `trajectory reaches target`: the current three `READY` weapon boxes can look like permission to hit even while the central message says the target is outside the arc. Put ammo purpose and lead adjustment beside the firing action at readable size; touch aiming also needs an obvious way to adjust lead, rather than only the current AIM L/AIM R hold buttons (`src/ui/Hud.ts:731,877–891`). The reference's conspicuous shot path/target association is the useful goal, not its painted effects. Acceptance: a new player can determine the selected battery, target, needed turn, and likely splash/hit location from one frame.

4. **P1 — Turn crew assignment into a visible command surface.** The current tiny crew-status strip is technically a button (`src/ui/Hud.ts:686,904–905`), and cycles five presets (`src/ui/Hud.ts:1270–1288`). That action is not evident in the supplied captures, particularly on touch where the `T` keycap is unhelpful. Provide a labeled CREW control with a recognizable icon and a direct picker for Gunnery/Sailing/Repair/Special/Balanced, showing current hand counts and the main benefit/cost before choosing. Keep the active order and a short acknowledgment visible in combat, and distinguish assigning repair hands from the separate REPAIR action. The reference's large gun/sail/hammer groups make crew roles readable immediately; the implementation does not yet translate that hierarchy. Acceptance: capture the expanded touch order picker and a changed-order state with clearly different allocation/effect feedback, without hiding the target or forcing blind cycling through presets.

5. **P2 — Expose the voyage economy at the decision point and verify its missing states.** Keep the route cards' strong names and explicit coin comparison, then add a small three-leg progression strip, readable risk/weather indicators, and an explicit distinction between contract payout, encounter payout, coins at risk, and banked coins. `Each build has a cost` currently describes tradeoffs in prose rather than presenting comparable benefit/penalty pairs. Harbor refits are one collapsed 7px label with zero bank shown; expose at least one recognizable refit preview/cost and indicate why it is unavailable. Give refit access a stronger, distinct action, as the next-voyage reference does. Code contains reward/extraction/result rendering, but none of those states were visually reviewed. Acceptance requires actual desktop/mobile captures for upgrade selection, an available refit, extraction/banking, and completion/failure; concept rewards or code templates cannot substitute for those states.

## What already works

- Desktop entry has a clear title, selected vessel outline, stat comparison, and a prominent next step. The mobile dock keeps the ship visible above the selection form.
- Contract and build selection use the same gold selected border and maintain a coherent reading order. Both actual portrait menu captures keep their main action within the supplied viewport.
- Route names, narrative descriptions, and explicit reward figures make the two desktop route choices distinguishable without interpretation.
- The combat HUD names the active ammo and side, and the aim state truthfully reports that the target is outside the firing arc.
- Input/controller state is cleared when input is disabled and on blur (`src/input/InputController.ts:58–60,113–129,178`; `src/runtime/GameApp.ts:354–359,390–393`). Touch handlers release held actions on pointer cancellation/lost capture (`src/ui/Hud.ts:888–891,915–918`). This is positive code evidence for interruption handling; no live interaction or controller test was performed in this review.
