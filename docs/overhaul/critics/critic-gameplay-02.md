## New actionable failures

1. **P1 — Accepted ledger state collides with the next voyage ID and prevents settlement.** In an extracted voyage-1 save, change the current voyage ID and corresponding sole ledger entry from `critic-gameplay-02:1` to `critic-gameplay-02:2`, leaving `totalVoyages=1`. Restore returns true. Return to harbor and start another voyage: `startVoyage()` increments to 2 and generates the already-paid ID. After a normal reward transition, extraction returns false and the new export is itself rejected on reload. Continued full completion also cannot settle because the paid-ID guard is permanent. Validator checks paid membership but not the seed/serial relationship (`saveValidation.ts:124–126`); ID generation and settlement rely on that missing invariant (`GameSimulation.ts:299–300`, `473–476`). Reject impossible ID/counter combinations and defensively avoid allocating an existing ID.

2. **P2 — Accepted reward state creates a duplicate permanent upgrade and an unloadable save.** Set a valid reward save to `upgrades=['powder']`, `rewardChoices=['powder','supplies']`. Restore returns true; `chooseReward('powder')` creates `['powder','powder']`; the resulting export is rejected by the validator's unique-string rule. `saveValidation.ts:71–85` validates both lists individually, but does not exclude already-owned permanent upgrades; `GameSimulation.ts:385–390` trusts the choice list. Validate the cross-list invariant and reject duplicate application at the command boundary.

3. **P2 — Battle target references may point at the player, making the encounter unwinnable.** Replace the one-enemy encounter's `targetIds` with `[state.playerId]`; restore returns true. Battle progress then requires the player to surrender, while the immediately preceding loss guard ends the voyage instead (`GameSimulation.ts:521–525`). `saveValidation.ts:123` proves only ID existence. Require actual non-player encounter enemies and validate escort-role relationships too.

4. **P2 — Known route IDs admit altered encounter kinds and rewards.** On the first Tempest route, keep its generated ID but set `kind='salvage'` and `reward=1000000`. Restore accepts both. `chooseRoute()` consumes those modified values directly. `saveValidation.ts:79–82` checks only that the ID appears in generated routes. Validate the full authored route record or rehydrate canonical route metadata from the accepted ID.

5. **P2 — Impossible storm progress completes at the spawn point.** In a freshly started storm encounter set only `progress=3` and `nextGate=3`, leaving `completed=false`, `elapsed=0`, and the player at spawn `(0,100)`. Restore returns true; one tick marks the encounter completed, and collection succeeds while the player remains at z=99.9997. Canonical gate coordinates are validated, but the progress/completion invariant is not. Since the tick resolves completion before any export can occur, full target progress with `completed=false` is not a legitimate end-of-tick state. Reject it. This probe demonstrates malformed-save acceptance, not an ordinary steering bypass or a requirement for cryptographic anti-cheat.

## Ordered storm passage and shared world

The normal storm algorithm crosses approach, arch, and exit in sequence. It checks northbound segment crossings and accounts for half the vessel beam inside each gate width (`GameSimulation.ts:529–539`). The existing ordinary-input tests reject the route around the arch/behind the exit and complete the proper route across reload. `LogicalWorld` supplies two arch pylons and leaves their central opening; collision/discovery tests pass. No normal-input bypass was established in this audit. Storm save acceptance still fails as item 5 above records.
